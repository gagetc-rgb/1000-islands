## Accessibility (W3C WCAG 2.2, https://www.w3.org/TR/WCAG22/ and Understanding documents)

- ◆ **Large text definition (1.4.3).** Source: https://www.w3.org/TR/WCAG22/ (glossary "large scale"). Quote: "large scale (text) with at least 18 point or 14 point bold or font size that would yield equivalent size for Chinese, Japanese and Korean (CJK) fonts". So "large text" = at least 18 pt, or at least 14 pt bold (not "24 px" in the normative text).
- ◆ **Contrast ratios (1.4.3).** Source: https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html. Quote: "The visual presentation of text and images of text has a contrast ratio of at least 4.5:1, except for the following: Large Text Large-scale text and images of large-scale text have a contrast ratio of at least 3:1". Also: "the computed values should not be rounded (e.g., 4.499:1 would not meet the 4.5:1 threshold)."
- ◆ **Reflow (1.4.10).** Source: https://www.w3.org/TR/WCAG22/. Quote: "Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels". Note: "320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom."
- ◆ **Target size, minimum (2.5.8, new in 2.2, Level AA).** Quote: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:" (spacing, equivalent, inline, user-agent-controlled, essential exceptions).

## Core Web Vitals (web.dev)

- ◆ **Thresholds table.** Source: https://web.dev/articles/defining-core-web-vitals-thresholds. Quote: "Largest Contentful Paint ≤2500 ms >4000 ms 75 Interaction to Next Paint ≤200 ms >500 ms 75 Cumulative Layout Shift ≤0.1 >0.25 75". (Good ≤ / Poor > / percentile 75.) So: LCP good ≤2.5 s, poor >4 s; INP good ≤200 ms, poor >500 ms; CLS good ≤0.1, poor >0.25.
- ◆ **LCP.** https://web.dev/articles/lcp: "To provide a good user experience, sites should strive to have Largest Contentful Paint of 2.5 seconds or less."
- ◆ **INP.** https://web.dev/articles/inp: "An INP above 200 milliseconds and below or at 500 milliseconds means a page's responsiveness needs improvement." and "An INP above 500 milliseconds means a page has poor responsiveness."
- ◆ **CLS.** https://web.dev/articles/cls: "To provide a good user experience, sites should strive to have a CLS score of 0.1 or less." and "Poor values are greater than 0.25."
- ◆ **Measured at the 75th percentile of field data.** https://web.dev/articles/vitals: "a good threshold to measure is the 75th percentile of page loads, segmented across mobile and desktop devices."
- ◆ **INP replaced FID.** https://web.dev/blog/inp-cwv-launch: "Interaction to Next Paint is now a stable Core Web Vital metric, replacing First Input Delay." and "developers will have until September 9, 2024 to transition over to INP." Also https://web.dev/articles/vitals: "This is exactly what happened to FID as INP became a stable Core Web Vital metric in 2024." (The exact "12 March 2024" date is not on these pages: not verified here.)

### More W3C WCAG 2.2 criteria (all from https://www.w3.org/TR/WCAG22/, verbatim)

- ◆ **2.4.7 Focus Visible (AA):** "Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible."
- ◆ **2.4.11 Focus Not Obscured (Minimum) (AA, new in 2.2):** "When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content."
- ◆ **3.3.1 Error Identification (A):** "If an input error is automatically detected, the item that is in error is identified and the error is described to the user in text."
- ◆ **3.3.2 Labels or Instructions (A):** "Labels or instructions are provided when content requires user input."
- ◆ **1.3.5 Identify Input Purpose (AA):** "The purpose of each input field collecting information about the user can be programmatically determined when: ..." (the autocomplete attribute is the usual technique).
- ◆ **3.3.7 Redundant Entry (A, new in 2.2):** "Information previously entered by or provided to the user that is required to be entered again in the same process is either: auto-populated, or available for the user to select."
- ◆ **3.3.8 Accessible Authentication (Minimum) (AA, new in 2.2):** "A cognitive function test (such as remembering a password or solving a puzzle) is not required for any step in an authentication process unless that step provides at least one of the following: Alternative ..."
- ◆ **2.2.2 Pause, Stop, Hide (A):** "For any moving, blinking or scrolling information that (1) starts automatically, (2) lasts more than five seconds, and (3) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it unless the movement, blinking, or scrolling is part of an activity where it is essential".
- ◆ **2.4.1 Bypass Blocks (A) (skip link):** "A mechanism is available to bypass blocks of content that are repeated on multiple web pages."
- ◆ **1.1.1 Non-text Content (A):** "All non-text content that is presented to the user has a text alternative that serves the equivalent purpose, except for the situations listed below." (Decorative images are one of the listed exceptions.)
- ◆ **1.4.4 Resize Text (AA):** "text can be resized without assistive technology up to 200 percent without loss of content or functionality."
- ◆ **1.4.12 Text Spacing (AA):** "Line height (line spacing) to at least 1.5 times the font size; Spacing following paragraphs to at least 2 times the font size; Letter spacing (tracking) to at least 0.12 times the font size; Word spacing to at least 0.16 times the font size." This is a "must not break when users override" test, not a design instruction.
- ◆ **1.4.8 Visual Presentation (AAA, so not required at AA):** "Width is no more than 80 characters or glyphs (40 if CJK). Text is not justified ... Line spacing (leading) is at least space-and-a-half within paragraphs". This is the only normative source for the common "~80 characters per line" rule; it is AAA, i.e. a best-effort target.
- ◆ **2.3.3 Animation from Interactions (AAA):** "Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed."

## Privacy and consent (EU law and regulators, fetched 11 Oct 2026)

All quotes are verbatim from the pages named. These are EU/UK/French sources; **nothing here is verified for Indonesian law** (UU PDP), which is "not verified / not researched beyond a candidate list".

- ◆ **GDPR applies to non-EU businesses that target EU visitors.** Regulation (EU) 2016/679, Art 3(2) (EUR-Lex https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679): "This Regulation applies to the processing of personal data of data subjects who are in the Union by a controller or processor not established in the Union, where the processing activities are related to: (a) the offering of goods or services, irrespective of whether a payment of the data subject is required, to such data subjects in the Union; or (b) the monitoring of their behaviour as far as their behaviour takes place within the Union."
- ◆ **Definition of consent.** GDPR Art 4(11): "‘consent’ of the data subject means any freely given, specific, informed and unambiguous indication of the data subject's wishes by which he or she, by a statement or by a clear affirmative action, signifies agreement to the processing of personal data relating to him or her".
- ◆ **Silence, pre-ticked boxes, inactivity.** GDPR Recital 32: "Silence, pre-ticked boxes or inactivity should not therefore constitute consent."
- ◆ **Withdrawal.** GDPR Art 7(3): "The data subject shall have the right to withdraw his or her consent at any time." and "It shall be as easy to withdraw as to give consent."
- ◆ **Service not conditional on unnecessary consent.** GDPR Art 7(4): "When assessing whether consent is freely given, utmost account shall be taken of whether, inter alia, the performance of a contract, including the provision of a service, is conditional on consent to the processing of personal data that is not necessary for the performance of that contract."
- ◆ **ePrivacy Directive 2002/58/EC as amended 2009, Art 5(3)** (EUR-Lex https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:02002L0058-20091219): "Member States shall ensure that the storing of information, or the gaining of access to information already stored, in the terminal equipment of a subscriber or user is only allowed on condition that the subscriber or user concerned has given his or her consent, having been provided with clear and comprehensive information, in accordance with Directive 95/46/EC, inter alia, about the purposes of the processing." with the exception for storage "strictly necessary in order for the provider of an information society service explicitly requested by the subscriber or user to provide the service."
- ◆ **CJEU Planet49 (C-673/17, 1 Oct 2019)** (https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62017CJ0673): "the consent referred to in those provisions is not validly constituted if, in the form of cookies, the storage of information or access to information already stored in a website user’s terminal equipment is permitted by way of a pre-checked checkbox which the user must deselect to refuse his or her consent." And (Q1(b)): the provisions "are not to be interpreted differently according to whether or not the information stored or accessed on a website user’s terminal equipment is personal data". And (Q2): "the information that the service provider must give to a website user includes the duration of the operation of cookies and whether or not third parties may have access to those cookies."
- ◆ **EDPB Guidelines 05/2020 on consent** (https://www.edpb.europa.eu/system/files/documents/files/file1/edpb_guidelines_202005_consent_en.pdf, text extracted from the PDF): "The use of pre-ticked opt-in boxes is invalid under the GDPR."; "Example 16: Based on recital 32, actions such as scrolling or swiping through a webpage or similar user activity will not under any circumstances satisfy the requirement of a clear and affirmative action"; "In order for consent to be freely given, access to services and functionalities must not be made conditional on the consent of a user to the storing of information, or gaining of access to information already stored, in the terminal equipment of a user (so called cookie walls)"; "Article 7(3) of the GDPR prescribes that the controller must ensure that consent can be withdrawn by the data subject as easy as giving consent and at any given time."
- ◆ **EDPB Cookie Banner Taskforce report, 18 Jan 2023** (https://www.edpb.europa.eu/system/files/documents/2023-01/edpb_20230118_report_cookie_banner_taskforce_en.pdf): "a vast majority of authorities considered that the absence of refuse/reject/not consent options on any layer with a consent button of the cookie consent banner is not in line with the requirements for a valid consent and thus constitutes an infringement."; "the TF members confirmed that the legal basis for the placement/reading of cookies pursuant to Article 5 (3) cannot be the legitimate interests of the controller."; "The taskforce members agreed that a general banner standard concerning colour and/or contrast cannot be imposed on data controllers." (so "equal prominence" is a case-by-case test, not a fixed rule).
- ◆ **CNIL (France): refusal as easy as acceptance.** https://www.cnil.fr/fr/cookies-et-autres-traceurs/regles/cookies/que-dit-la-loi — "L'utilisateur doit pouvoir accepter ou refuser le dépôt et/ou la lecture des cookies avec le même degré de simplicité."
- ◆ **CNIL (France): audience-measurement cookies can be exempt from consent only under conditions** (page dated 4 July 2025, https://www.cnil.fr/fr/cookies-solutions-pour-les-outils-de-mesure-daudience): "Les cookies déposés dans cet objectif peuvent être exemptés de consentement sous certaines conditions." The conditions include: "être utilisés pour une finalité strictement limitée à la seule mesure de l’audience du site ou de l’application ... pour le compte exclusif de l’éditeur" and "servir à produire des données statistiques anonymes uniquement"; they must not "conduire à un recoupement des données avec d’autres traitements ou à ce que les données non anonymes soient transmises à des tiers" nor "permettre le suivi global de la navigation de la personne".
- ◆ **ICO (UK)** guidance page https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/ contains a section titled "What is the ‘statistical purposes’ exception?" (the detail was not extracted; **the exact UK statistical exception wording is not verified here**).

## Domains, DNS, email records, hosting hand-off (fetched 11 Oct 2026)

- ◆ **CNAME exclusivity.** RFC 1034 (https://www.rfc-editor.org/rfc/rfc1034.html): "If a CNAME RR is present at a node, no other data should be present; this ensures that the data for a canonical name and its aliases cannot be different." (Why a CNAME cannot sit on a root/apex name that also carries NS, SOA and MX records, as Kirilenko Pro says.)
- ◆ **Negative caching is a standard.** RFC 2308 (https://www.rfc-editor.org/rfc/rfc2308.html), "Negative Caching of DNS Queries (DNS NCACHE)", updates RFC 1034 and 1035: "Negative caching was an optional part of the DNS specification and deals with the caching of the non-existence of an RRset [RFC2181] or domain name." (Backs the "I created the record but still get NXDOMAIN" explanation.)
- ◆ **SPF and DMARC definitions.** RFC 7208: "whereby ADministrative Management Domains (ADMDs) can explicitly authorize the hosts that are allowed to use their domain names, and a receiving host can check such authorization." RFC 7489: "DMARC is a mechanism for policy distribution that enables increasingly strict handling of messages that fail authentication checks, ranging from no action, through altered delivery, up to message rejection." (DKIM, RFC 6376, was not fetched.)
- ◆ **Cloudflare TTL facts** (https://developers.cloudflare.com/dns/manage-dns-records/reference/ttl/): "proxied records have a TTL of Auto, which is set to 300 seconds."; "For DNS only records, you can choose a TTL between 30 seconds (Enterprise) or 60 seconds (non-Enterprise) and 1 day." This **contradicts** the Backend Deep Dives claim of a 1-second minimum for paid plans (video 9:09).
- ◆ **Cloudflare Pages custom domains** (https://developers.cloudflare.com/pages/configuration/custom-domains/): "If you are deploying to an apex domain (for example, example.com), then you will need to add your site as a Cloudflare zone and configure your nameservers." and, once nameservers point to Cloudflare, "Cloudflare will proceed by creating a CNAME record for you."
- ◆ **Gmail sender rules** (https://support.google.com/a/answer/81126): "Set up SPF or DKIM email authentication for your sending domains." for all senders; "Starting February 1, 2024, email senders who send more than 5,000 messages per day to Gmail accounts must meet the requirements in this section." (the bulk-sender rules include DMARC); "To pass DMARC authentication, messages must be authenticated by SPF or DKIM, or both." A small business sending far fewer messages is not under the bulk rules, but SPF/DKIM are still advised.
- Not verified: the "24 to 48 hours" propagation after a name-server change (Backend Deep Dives, Stewart Gauld); ICANN transfer-lock rules (page not fetched); registrar pricing in the videos; any statement that a particular host is "best".

## Forms and conversion (fetched 11 Oct 2026)

- ◆ **Placeholder is not a label** (GOV.UK Design System, text input, https://design-system.service.gov.uk/components/text-input/): "Avoid placeholder text Do not use placeholder text in place of a label, or for hints or examples, as: it vanishes when the user starts typing, which can cause problems for users with memory conditions or when reviewing answers not all screen readers read it out its browser default styles often do not meet WCAG 2.2 success criterion 1.4.3 Contrast (minimum)". - ◆ **MDN input placeholder** (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input): "Note: The placeholder attribute is not as semantically useful as other ways to explain your form, and can cause unexpected technical issues with your content."
- ◆ **Optional marking** (GOV.UK question pages, https://design-system.service.gov.uk/patterns/question-pages/): "If you ask for optional information: in most contexts, add ‘(optional)’ to the labels of optional fields" and "only ask users for information you really need".
- ◆ **Error message pattern** (https://design-system.service.gov.uk/components/error-message/): "For each error: put the message in red after the question text and hint text; use a red border to visually connect the message and the question it belongs to" and "To help screen reader users, the error message component includes a hidden ‘Error:’ before the error message." Error summary (https://design-system.service.gov.uk/components/error-summary/): "Put the error summary at the top of the main container."
- ◆ **GOV.UK on HTML5 validation** (https://design-system.service.gov.uk/patterns/validation/): "Do not use it because: the visual style, placement and content of HTML5 error messages cannot be made consistent with the GOV.UK Design System we know that the GOV.UK Design System error message and error summary components are accessible. To turn off HTML5 validation, add ‘novalidate’ to your form tags." (This **contradicts** the Silktide talk, which recommends native browser validation; both aim at accessibility.)
- ◆ **Labels and autocomplete** (web.dev, https://web.dev/articles/payment-and-address-form-best-practices): "Label each form field with a <label>." and "Use HTML element attributes to access built-in browser features, in particular type and autocomplete with appropriate values."
- ◆ **WCAG 1.4.11 Non-text Contrast (AA)** (https://www.w3.org/TR/WCAG22/): "The visual presentation of the following have a contrast ratio of at least 3:1 against adjacent color(s): User Interface Components Visual information required to identify user interface components and states". (Backs the Silktide point that pale field boundaries can fail.)
- ◆ **WCAG 3.3.7 Redundant Entry (A)**: "Except when: re-entering the information is essential, the information is required to ensure the security of the content, or previously entered information is no longer valid." So confirm-password fields are permitted by the standard; "do not ask twice" is a usability argument, not a WCAG failure.
- ◆ **WCAG 2.5.5 Target Size (Enhanced) (AAA)**: "The size of the target for pointer inputs is at least 44 by 44 CSS pixels" (the 24 px minimum at AA is 2.5.8, verified earlier). Sabot's "48 px" is a platform guideline, not WCAG.
- ◆ **Baymard (current figures)** (https://baymard.com/blog/checkout-flow-average-form-fields): "In 2024, the average checkout has 5.1 steps." and "we’ve found that most sites need only 8 form fields in total for a checkout flow — yet the average in 2024 was 11.3 form fields (slightly down from 11.8 in 2021 and 12.7 in 2019)." and "what really matters to the overall UX of checkout is the number of form fields users must consider." (The 2019 video quoted 12.8 fields; the later page gives 12.7 for 2019, a small revision.) Cart abandonment page (https://baymard.com/lists/cart-abandonment-rate): average "calculated based on 50 different studies" (the 2019 video said 41); reasons list includes "17 % Too long / complicated checkout process" (the 2019 video said 26% of users abandoned an order in the past quarter for a too complicated checkout; the two are different measures and years).
- Not verified: Friedman's "400 ms to switch between keyboard and mouse", "autofill reduces completion time by at least 30%" and "almost 70% of non-technical users copy-paste" (sources not named); Expedia's "$12 million" form-field story (told by Grundy); "twice as likely to be submitted without errors"; the threshold-validation pattern's author attribution.

## Typography and web fonts (fetched 11 Oct 2026)

- ◆ **font-display** (https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face/font-display): "swap Gives the font face an extremely small block period and an infinite swap period." "optional Gives the font face an extremely small block period and no swap period." and "Font block period: If the font face is not loaded, any element attempting to use it must render an invisible fallback font face."
- ◆ **WOFF2** (https://web.dev/articles/font-best-practices): "Of the modern font fonts, WOFF2 is the newest, has the widest browser support, and offers the best compression."
- ◆ **Preload has a cost** (same page): "preload is highly effective at making fonts discoverable early in the page load process, this comes at the cost of taking away browser resources from the loading of other resources." (backs "preload one or two fonts, not all")
- ◆ **font-display: swap and layout shift** (same page): "font-display: swap but make sure to deliver the font early enough that it does not cause a layout shift."
- ◆ **Self-hosting** (same page): "On paper, using a self-hosted font should deliver better performance as it eliminates a third-party connection setup." (Leatherman measured no gain in one test; so treat as ◈ "worth measuring").
- ◆ **Variable fonts** (same page): "a single variable font can be used as a replacement for multiple font files." (Leatherman cautions the single file can be larger than one static file.)
- ◆ **unicode-range** (https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face/unicode-range): "The unicode-range CSS descriptor sets the specific range of characters to be used from a font defined using the @font-face at-rule and made available for use on the current page."
- ◆ **Text resize** (WCAG 2.2 Understanding 1.4.4, https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html): "If the resizing mechanism ... offers incremental resizing steps between 100% and 200%, authors must ensure that there is no loss of content or functionality at these incremental steps." (Supports Pamental's warning that viewport-unit-only sizing breaks zoom; the Understanding page excerpt fetched does not name viewport units explicitly: **the vw point is ◇ his claim, backed by the general requirement**.)
- ◆ **Text spacing and line length** (WCAG 2.2, verified earlier): 1.4.12 requires that content survives user line height 1.5, paragraph spacing 2x, letter spacing 0.12 and word spacing 0.16 of the font size; 1.4.8 (AAA) "Width is no more than 80 characters or glyphs (40 if CJK). Text is not justified".
- ◆ **Cyrillic support (live check):** Google Fonts' CSS API (https://fonts.googleapis.com/css2?family=...) returned subset blocks `cyrillic-ext` and `cyrillic` for Oswald, Roboto and Montserrat, and `cyrillic` for Playfair Display. Hence Easyweb Academy's 2016 statement that Oswald has no Cyrillic is **out of date**; Photofox's "Helvetica has no Cyrillic" refers to the system Helvetica on macOS and was **not verified** (Helvetica is not a Google Font).
- Not verified: Pamental's "50% improvement in reading cognition" for crowding (Microsoft research relayed second-hand); Photofox's claim that small serif text is unusable on screens; Pamental's "75% of users leave if the site has not loaded in 5 seconds" (unsourced, 2016).

## Images for websites (fetched 11 Oct 2026)

- ◆ **Two different tools: resolution switching vs art direction** (MDN, https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images): "Responsive image technologies ... letting you offer the browser several image files, either all showing the same thing but containing different numbers of pixels (resolution switching), or different images suitable for different space allocations (art direction)." and "The general problem whereby you want to serve different cropped images in that way, for various layouts, is commonly known as the art direction problem." (Backs the Drupal talk's core point: `srcset`/`sizes` for the same picture, `<picture>` for different crops.)
- ◆ **`<picture>` is for art direction** (MDN `<picture>`, https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/picture): "Common use cases for <picture>: Art direction." and "the user agent examines each <source>'s srcset, media, and type attributes to select a compatible image that best matches the current layout and capabilities of the display device."
- ◆ **`<picture>` is a wrapper around a fallback `<img>`** (web.dev Learn Images, https://web.dev/learn/images/prescriptive): "The <picture> element doesn't render anything on its own, but instead acts as a decision engine for an inner <img> element, telling it what to render." and "You should always specify the inner img last in the order"; also "Making changes to the content or aspect ratio of an image based on the size of the image in the page is typically referred to as 'art directed' responsive images."
- ◆ **`sizes` is required with width descriptors** (web.dev, https://web.dev/learn/design/responsive-images): "If you're using the width descriptor, you must also use the sizes attribute to give the browser more information." and "add multiple versions of the same image at different sizes, and use the srcset attribute to tell the browser these sizes exist and when to use them."
- ◆ **Set width and height on images (layout shift)** (web.dev, https://web.dev/articles/optimize-cls): "Images without dimensions Always include width and height size attributes on your images and video elements." (also listed there as the most common cause of poor CLS). web.dev Learn Images (same prescriptive page) says width/height on `<source>` "reduce layout shifts just as well as they do on <img>".
- ◆ **Do not lazy-load the hero/LCP image** (web.dev, https://web.dev/articles/browser-level-image-lazy-loading): "Don't lazy-load images that are likely to be in-viewport when the page loads, especially LCP images." and "Always eager-load images visible in the first viewport". Second source (https://web.dev/articles/optimize-lcp): "Never lazy-load your LCP image, as that will always lead to unnecessary resource load delay, and will have a negative impact on LCP." Same page: "If you want to increase the fetch priority of an important image (for example, the LCP image), use Fetch Priority with fetchpriority="high"."
- ◆ **Cropping in CSS: `object-fit` and `object-position`** (MDN, https://developer.mozilla.org/en-US/docs/Web/CSS/object-fit and /object-position): `cover`: "The replaced content is sized to maintain its aspect ratio while filling the element's entire content box."; "The object-position CSS property specifies the alignment of the selected replaced element's contents within the element's box." Initial value `50% 50%` (so a centred crop by default: a face placed high or low in the photo can be cut unless the position is set per image or a different file is used). The "cut" consequence is my reading of the initial value, not a quoted sentence.
- ◆ **Formats and support** (web.dev Learn Images): "AV1 Image File Format (AVIF) is an encoding based on the open source AV1 video codec." and "AVIF is even newer than WebP, only supported in Chrome and Opera since 2020, Firefox in 2021, and Safari in 2022." (https://web.dev/learn/images/avif). Use the `<picture>` `type` attribute to offer a fallback; none of the six imagery videos mentions WebP/AVIF.
- ◆ **Alt text and file names for search** (Google Search Central, https://developers.google.com/search/docs/appearance/google-images): "When possible, use filenames that are short, but descriptive." and "The most important attribute when it comes to providing more metadata for an image is the alt text (text that describes an image), which also improves accessibility for people who can't see images on web pages". Backs Silva's advice on descriptive names/alt text; WCAG 1.1.1 quote is in the Accessibility section above.
- ◆ **Text over photos must still meet contrast** (WCAG 1.4.3, see the Accessibility section: "contrast ratio of at least 4.5:1"). The videos (Flux, Gray) say "leave space and contrast"; the measurable requirement is the WCAG ratio against the actual pixels behind the text.
- ◆ **Pexels licence** (https://www.pexels.com/license/): "All photos and videos on Pexels are free to use." "Attribution is not required." "Identifiable people may not appear in a bad light or in a way that is offensive." "Don't sell unaltered copies of a photo or video, e.g. as a poster, print or on a physical product without modifying it first." (Supports Silva's "read the licence": the terms differ per site. Pixabay's licence page returned an HTTP error to my fetch, so **Pixabay terms: not verified**.)
- ◆ **Social share image size** (see Search and sharing above): Meta "at least 1200 x 630 pixels for the best display on high resolution devices", minimum 200 x 200, file under 8 MB.
- Not verified: Gray's "about 60/40" mobile share (spoken estimate; check the site's own analytics); her "70-72 DPI" and "400 KB / 2,000 px" targets; Silva's "under 100 KB"; Segall's stock prices "one to five dollars"; the Drupal talk's "images are about 60 percent of page traffic" (2017, unsourced; HTTP Archive would be the place to check, not fetched); Facebook Sharing Debugger's current UI (not re-fetched).

## Search basics: content, page experience, headings, canonical, JavaScript (fetched 11 Oct 2026)

- ◆ **Relevance beats page experience** (Google Search Central, https://developers.google.com/search/docs/appearance/page-experience): "Google Search always seeks to show the most relevant content, even if the page experience is sub-par." and "Core Web Vitals are used by our ranking systems." and "Site owners seeking to be successful with our systems shouldn't focus on only one or two aspects of page experience." (Backs the Chrome SEO talk [8:09] and the Fireship "content first" rule; the 2020-21 "page experience ranking factor" wording in the Chrome talk is historical: the page now asks "Is there a single 'page experience signal' that Google Search uses for ranking?" as a FAQ.)
- ◆ **Headings are for users** (SEO Starter Guide, https://developers.google.com/search/docs/fundamentals/seo-starter-guide): "Break up long content into paragraphs and sections, and provide headings to help users navigate your pages." Google's text gives the user benefit; it does not state that words in headings weigh more for ranking (the Easyweb claim is therefore **not verified**).
- ◆ **Descriptive URLs** (same guide): "Use descriptive URLs Parts of the URL can be displayed in search results as breadcrumbs, so users can also use the URLs to understand whether a result will be useful for them."
- ◆ **Canonicalisation signals** (https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls): "These are, in order of how strongly they can influence canonicalization: Redirects: A strong signal that the target of the redirect should become canonical. rel="canonical" link annotations: A strong signal that the specified URL should become canonical." and "Sitemap inclusion: A weak signal that helps the URLs that are included in a sitemap become canonical." (Backs midulive's advice: redirect www and non-www to one version; canonical as a hint, not a command.)
- ◆ **JavaScript pages are processed in phases** (https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics): "Google processes JavaScript web apps in three main phases: Crawling Rendering Indexing. Googlebot queues pages for both crawling and rendering." So Fireship's "reliability is questionable" for client-side apps is a statement about delay/risk, not a claim that Google cannot render; social-preview crawlers (Facebook, X) were not checked and are not covered by this page.
- Not verified: Fireship's "over 200 factors", bounce rate and dwell time as ranking signals (no page fetched supports these); Easyweb's heading-weight claim; the "Twitter card validator" tool's current state.
